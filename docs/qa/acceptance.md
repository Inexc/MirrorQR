# «Экран по QR» — план приёмки (QA)

**Статус: план проверки, а не отчёт.** Ни один сценарий ниже ещё не выполнялся. В
`matrix.json` все сценарии имеют `status: "not_run"`. Запуск приложения, серверов, браузера и
общих тестов — задача тимлида при интеграции; QA-часть только описывает воспроизводимые шаги.

## 1. Что проверяем и на каком контракте

| Параметр | Значение |
|---|---|
| Порт локального сервера | `8765` (конфигурация порта не меняется) |
| Страница телефона | `GET http://<LAN-IP>:8765/phone` |
| Статика | `GET /assets/phone.css`, `GET /assets/phone.js` (только файлы из `web/`) |
| WebSocket | `ws://<LAN-IP>:8765/ws` |
| Порядок сообщений | `auth` → `ready` → `offer` → `answer` |
| ICE | **non-trickle**: кандидаты внутри SDP, отдельных сообщений `candidate` нет; `iceServers: []` |
| Медиа | только video, `recvonly`, направление компьютер → телефон |
| Клиенты | **один активный**; второй получает `{"type":"error","code":"busy"}` |
| Отказ захвата | `{"type":"error","code":"capture_unavailable"}` и следом `{"type":"ended","reason":"capture_failed"}` |
| Завершение | `{"type":"stop"}` → `{"type":"ended","reason":"stopped"}`; при обрыве — `disconnected` |
| Порядок освобождения | `peer.close()` → `track.stop()` → ожидание `cleanup_task` (если он есть) → закрытие loop |
| Повторная попытка | только новый QR; погашенный токен не переиспользуется |

Границы MVP: одно направление (комп → телефон), одна локальная сеть, без TURN/интернета,
без управления мышью/тачем, без виртуального монитора, без звука.

## 2. Что уже известно статически (не является прогоном)

Эти факты прочитаны в коде при подготовке плана, но **не проверены запуском**:

- `src/capture/factory.py` на `win32` сразу бросает `RuntimeError`: привязки Windows.Graphics.Capture
  и системного picker нет. Значит на Windows ожидаем отказ `capture_unavailable`, а не поток.
- `src/backend/signaling.py:148-152` — слот проверяется **до** `redeem()`, поэтому `busy` не
  погашает токен и не трогает состояние первого клиента.
- `src/backend/signaling.py:236-248` — в `finally`: `peer.close()`, затем `track.stop()`, затем
  `await asyncio.wait_for(asyncio.shield(cleanup), timeout=5.0)` для `track.cleanup_task`.
- Linux-адаптер (`src/capture/linux.py`, `src/capture/portal.py`) — непроверенный код: portal,
  PipeWire и GStreamer сквозным запуском не подтверждены.

Отсюда разделение: **QA-03** — ожидаемый отказ Windows, **QA-08** — Linux-сценарий, который
требует реальной интерактивной сессии с portal и PipeWire и может быть не выполнен.

## 3. Как отличить реальный захват от заглушки

1. **Живое движение.** На экране компа — часы с секундами или перетаскивание окна; на телефоне
   картинка меняется в пределах ~1 с. Статичный кадр = провал.
2. **Совпадение содержимого.** На экране компа открыто окно с уникальной случайной строкой; этот
   же текст читается на телефоне.
3. **Отсутствие MJPEG.** В DevTools телефона (Network) нет запросов `image/jpeg` или
   `multipart/x-mixed-replace`; трафик идёт через `RTCPeerConnection`.
4. **Отказ вместо подмены.** Нет разрешения/portal — только `capture_unavailable`, без тестового
   изображения и без захвата произвольного монитора вместо системного picker.

## 4. Сценарии (8, порядок совпадает с `matrix.json`)

Приоритеты: **P0** — блокирует MVP, **P1** — важный, но не блокирующий.

### QA-01 (P0) Базовый сеанс: /phone, /assets/*, /ws и WS auth → ready → offer → answer

**Предусловия:** Python 3.11 и зависимости установлены; порт 8765 свободен; компьютер и телефон
в одной LAN; на телефоне браузер с WebRTC; на Linux доступна интерактивная сессия с portal и
PipeWire (на Windows базовый сеанс с видео не выполнить — см. QA-03).

**Шаги:** запустить `python main.py`; выбрать LAN-IPv4 в `networkSelector`, нажать `startButton`;
на компьютере открыть `/phone`, `/assets/phone.css`, `/assets/phone.js`; отсканировать QR;
в DevTools телефона (Network → WS) записать кадры; проверить адресную строку и SDP.

**Ожидаемо:** `/phone` отдаёт HTML, `/assets/phone.css` — CSS, `/assets/phone.js` — JS, все 200;
порядок WS строго `auth` → `ready` → `offer` → `answer`; в `ready` есть `sessionId`; в SDP нет
отдельных `candidate`; после загрузки в адресной строке нет `#token=`; на телефоне видно
движение (проверка §3); на desktop `statusLabel` «Трансляция», `clientConnected=true`.

### QA-02 (P0) Второй клиент: busy, первая сессия и токен не пострадали

**Предусловия:** телефон A уже в сессии (QA-01 или QA-08); действующий токен для B известен
(тот же URL A или токен, выпущенный до подключения A); телефон B в той же сети.

**Шаги:** снять snapshot до подключения B (`status`, `clientConnected`, `pairingUrl`,
`tokenExpiresAt`); открыть на B URL с действующим токеном; в DevTools B записать ответ сервера;
снять snapshot после; наблюдать A ещё 30 секунд; повторить подключение B тем же токеном.

**Ожидаемо:** B получает `{"type":"error","code":"busy"}` и текст «К компьютеру уже подключён
другой телефон…», видео у B нет, WebSocket закрыт; сессия A не прерывается, `clientConnected`
остаётся `true`; **токен не погашен**: `pairingUrl` и `tokenExpiresAt` те же, повторный заход B
снова даёт `busy`, а не `invalid_token`; `refreshQrButton` недоступна.

### QA-03 (P0) Windows: ожидаемый отказ захвата — capture_unavailable + ended capture_failed

**Предусловия:** Windows 10/11, зависимости установлены, окно приложения открывается; известно,
что адаптера WGC и системного picker в этой поставке нет; телефон в той же LAN.

**Шаги:** запустить `python main.py`, выбрать адрес, `startButton`; открыть QR телефоном;
дождаться `auth` → `ready` → `offer`; записать в DevTools всё, что пришло после `offer`; снять
snapshot; проверить, что видео на телефоне нет.

**Ожидаемо:** сервер присылает `{"type":"error","code":"capture_unavailable"}` и сразу
`{"type":"ended","reason":"capture_failed"}`; телефон показывает «Компьютер не может захватить
экран. Проверьте разрешение на запись экрана.» и подсказку отсканировать новый QR; кнопка
«Показать видео» не появляется; на desktop `statusLabel` «Ошибка: Захват экрана недоступен.»
(или «Ошибка: …»), `clientConnected=false`; тестовых кадров и захвата произвольного монитора нет.
Это **ожидаемый** результат, а не успех: Windows не считается поддерживаемой.

### QA-04 (P0) Ручной запуск видео при запрете autoplay

**Предусловия:** рабочая сессия с видео (Linux, QA-01/QA-08); браузер телефона блокирует
autoplay (Safari iOS с ограничением автовоспроизведения или Chrome с отключённым autoplay).

**Шаги:** открыть страницу по QR и дождаться состояния «Трансляция готова»; проверить, что
`playButton` «Показать видео» видна и не перекрыта; нажать её; проверить, что оверлей скрылся и
видео идёт; с внешней клавиатуры пройти Tab до `playButton` и нажать Enter/Space.

**Ожидаемо:** при заблокированном autoplay видна кнопка «Показать видео» и текст «Браузер не
запустил видео автоматически.»; оверлей не перехватывает нажатие (кликабельна только панель);
после нажатия видео идёт и показывает движение; у кнопки видимый фокус и она доступна с
клавиатуры; если autoplay не заблокирован, кнопка не показывается.

### QA-05 (P0) Завершение «Стоп» и повторный запуск без блокировки порта

**Предусловия:** активная сессия с видео (Linux); доступны `netstat`/`ss` для проверки 8765.

**Шаги:** нажать «Стоп» на телефоне, записать сообщение; дождаться `clientConnected=false`;
нажать `stopButton` на компьютере; проверить, что порт 8765 свободен; запустить `python main.py`
снова, `startButton`, новый QR; подключить телефон; открыть старый URL.

**Ожидаемо:** телефон после «Стоп» показывает «Просмотр завершён / Вы остановили трансляцию.» и
подсказку про новый QR; сервер отдал `ended` с `reason=stopped`; после остановки порт 8765
свободен, повторный запуск проходит без «адрес занят»; новая сессия показывает реальное видео;
старый токен даёт `invalid_token`.

### QA-06 (P1) Обрыв связи: ended disconnected и отсутствие автопереподключения

**Предусловия:** активная сессия с видео; возможность отключить Wi-Fi на 10–20 секунд.

**Шаги:** отключить Wi-Fi на телефоне; вернуть его; открыть страницу заново; проверить
сообщения на телефоне и состояние desktop; открыть старый URL.

**Ожидаемо:** сервер завершает сессию с `ended` `reason=disconnected` (или по таймауту WebRTC),
освобождает слот и track; телефон показывает «Связь с компьютером прервана.» и не переподключается
с тем же токеном; desktop возвращается в «Ожидание телефона» (или «Ошибка»), окно не зависает,
`refreshQrButton` доступна; старый токен даёт `invalid_token`.

### QA-07 (P0) Linux: освобождение захвата — peer.close() → track.stop() → cleanup_task до закрытия loop

**Предусловия:** Linux с интерактивной сессией: DBus, xdg-desktop-portal и backend portal
рабочего стола, PipeWire, GStreamer 1.0 с `pipewiresrc`; сессия уже установлена (QA-08);
терминал с `python main.py` виден для чтения логов.

**Шаги:** завершить сессию на телефоне или `stopButton`; читать вывод приложения; проверить в
журнале portal, что сессия закрыта и PipeWire-поток не остался; запустить приложение и сессию
снова; искать в логах «Task was destroyed but it is pending» и «Event loop is closed».

**Ожидаемо:** порядок `peer.close()` → `track.stop()` → ожидание `track.cleanup_task` до
закрытия loop; трейсбеков при закрытии нет; повторный запуск не блокируется осиротевшим
portal-сеансом; «Linux cleanup подтверждён» можно заявлять только после этого сценария — до него
он остаётся неподтверждённым.

### QA-08 (P1) Linux: реальный захват через portal и PipeWire (неподтверждённый сценарий)

**Предусловия:** Linux с Wayland (или X11 с работающим portal), интерактивная пользовательская
сессия; PyGObject, GStreamer 1.0, GstVideo 1.0 и плагины pipewire установлены в том же
интерпретаторе Python 3.11; xdg-desktop-portal и backend portal рабочего стола запущены.

**Шаги:** запустить приложение, `startButton`, открыть QR; пройти системный диалог выбора
источника; зафиксировать, что пришёл `answer`, а не `error`; сверить уникальную строку и движение
(§3); завершить сессию и перейти к QA-07; повторить на конфигурации без portal/PipeWire.

**Ожидаемо:** portal выбирает ровно один источник, PipeWire отдаёт кадры, на телефоне видно
реальное видео; на конфигурации без portal/PipeWire — `capture_unavailable` и `ended`
`capture_failed` без тестового изображения; Linux не объявляется поддерживаемой, пока шаги не
пройдены. Сценарий отделён от Windows-отказа (QA-03): там ожидаемый отказ, здесь — проверка
реального захвата.

## 5. Что остаётся непроверенным до интеграции

- Все 8 сценариев — `not_run`; выполняет тимлид при интеграции.
- QA-01, QA-04, QA-05, QA-07, QA-08 требуют Linux-машины с интерактивной сессией и portal/PipeWire;
  на Windows выполнимы только QA-02, QA-03, QA-06.
- Задержка не измеряется и не гарантируется этим планом.
- К отчёту прикладываются скриншоты/видео с телефона и логи без токенов и SDP.
